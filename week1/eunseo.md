# NAT

NAT는 Network Address Translation이다. 패킷의 주소 정보를 바꾸는 기능이다.

- **Netfilter & Hook:** 패킷이 지나가는 경로에 설치된 훅. 대표적으로 `PREROUTING`과 `POSTROUTING`이 있다.
- **Conntrack (연결 추적):** 연결의 상태를 기록하는 곳. **첫 번째 패킷**만 NAT 규칙을 검사하여 장부에 기록하고, 이후 패킷들은 기록만 확인하여 고속으로 주소를 변환한다. (규칙 재검사 생략)
- **iptables / nftables:** Netfilter Hook에 사용자 정의 NAT 규칙을 삽입하고 관리하는 도구이다.

## DNAT와 SNAT

NAT은 크게 두 가지로 나뉜다. SNAT은 Source NAT, 즉 출발지 주소를 바꾸는 것이다. DNAT은 Destination NAT, 즉 목적지 주소를 바꾸는 것이다. 필요하면 주소뿐만 아니라 포트도 함께 바꿀 수 있어서, 포트 포워딩 같은 것도 가능하다.

- DNAT : 외부에서 공유기의 Public IP로 접근했을 때, 이 요청은 내부의 Private IP 이 곳으로 보내야 한다고 목적지를 바꾸는 상황 (포트포워딩)
    - PREROUTING → Routing Decision
    - **목적지 설정**을 미리 안 하고 라우팅을 할 순 없다.
- SNAT :  랜 망 안에서 Private IP를 각각 가지고 있는 기기들이 인터넷을 할 때, 공유기가 자신의 Public IP로 출발지를 둔갑(?) 시켜 밖으로 내보내는 상황
    - Routing Decision → POSTROUTING
    - **출발지 설정**을 미리 해야 라우팅을 할 수 있다.

```jsx
[외부 진입] 
 NIC 
  ↓
 PREROUTING   (★ DNAT 발생: 길 찾기 전에 목적지 수정)
  ↓
 Routing Decision (길 찾기)
  ├─ [로컬 목적지] → INPUT → Local Process
  └─ [타겟 포워딩] → FORWARD → POSTROUTING (★ SNAT 발생: 나가기 직전 출발지 수정) → NIC [외부 퇴장]
```

+) 라우팅 결과, 패킷의 최종 목적지가 자기 노드 안에 있을 때
패킷을 다른 곳으로 포워딩하지 않고, INPUT 훅을 바로 거쳐서 서버 내부로 바로 전달된다.

# Kubernetes 에서의 DNAT

가상의 서비스 IP(ClusterIP)를 실제 일하는 파드(Pod)의 IP로 변환하여 길을 찾아갈 수 있도록…

1. 클라이언트 요청: 클라이언트(다른 Pod)가 프론트엔드 서비스의 가상 IP (ClusterIP: `10.96.0.10`)로 요청을 보냅니다.
2. 노드 진입: 패킷이 워커 노드의 네트워크 스택(NIC 또는 가상 인터페이스)에 막 도착합니다.
3. PREROUTING 훅 도달: 패킷은 커널이 라우팅(길 찾기)을 시작하기도 전에, 들어오자마자 `PREROUTING` 훅에 걸립니다.
4. kube-proxy 규칙 개입: `kube-proxy`가 미리 해당 훅에 작성해둔 iptables(또는 IPVS) 규칙이 발동합니다.
    - 목적지가 `10.96.0.10`(Service IP)이네? 이 IP는 실제로 존재하지 않는 가짜 주소니까, 실제 연결되어 있는 백엔드 파드 IP(`10.244.1.5`) 중 하나로 목적지를 바꿔주자!
5. DNAT 적용 및 라우팅: 목적지 주소가 파드 IP로 변경(DNAT)되었습니다. 이제 커널은 변경된 목적지(`10.244.1.5`)를 기준으로 라우팅 테이블을 뒤져서, 이 패킷을 어느 가상 인터페이스(cni0 등)로 보낼지 정확한 길을 찾습니다.

# Kubernetes 에서의 SNAT

파드(Pod)가 노드 외부(다른 노드나 인터넷)와 통신할 때, 응답 패킷이 길을 잃지 않고 돌아올 수 있도록 출발지 IP를 노드의 IP로 위장

1. 파드의 외부 통신 시도: 내부 파드(IP: `10.244.1.5`)가 인터넷에 있는 구글 서버(`8.8.8.8`)나 다른 노드에 있는 파드로 패킷을 보냅니다.
2. 라우팅 결정 (길 찾기 완료): 커널이 라우팅 테이블을 확인합니다. "목적지가 외부망이네. 이 패킷은 노드의 메인 랜카드(eth0)를 통해서 밖으로 내보내야겠다."
3. POSTROUTING 훅 도달: 길을 다 찾고, 패킷이 메인 랜카드를 통해 노드를 빠져나가기 직전 `POSTROUTING` 훅에 걸립니다.
4. CNI / kube-proxy 규칙 개입: 네트워크 플러그인(CNI)이나 `kube-proxy`가 설정한 마스커레이드(Masquerade) 규칙이 발동합니다.
    - 출발지가 파드 IP(`10.244.1.5`)인 상태로 인터넷에 나가면, 구글 서버는 이 사설 IP로 응답을 돌려보낼 방법이 없어. 나가는 문(eth0)에 할당된 진짜 노드 IP(`192.168.1.100`)로 출발지를 위장해서 내보내자!
5. SNAT 적용 및 퇴장: 패킷의 출발지 주소가 노드의 IP로 변경(SNAT)되어 밖으로 나갑니다. 외부 서버는 노드 IP로 응답을 보내고, 노드는 Conntrack(연결 추적 장부)을 확인하여 응답 패킷의 목적지를 다시 파드 IP로 역변환하여 전달해 줍니다.

# CKA 트러블슈팅 예시 문제

## Service 를 만들었는데 접속이 안 돼요

- **증상:** 클라이언트 파드에서 `10.96.x.x` (ClusterIP)로 `curl`을 날렸는데 타임아웃이 떨어집니다.
- **원리 (DNAT):** PREROUTING 훅에서 목적지를 파드 IP로 바꿔줄 규칙(DNAT)이 아예 생성되지 않은 상태입니다. 왜 안 만들어졌을까요? Service의 `selector` 라벨과 실제 파드의 라벨이 매칭되지 않아, 목적지 명단인 `Endpoints`가 비어있기 때문입니다. kube-proxy는 endpoint를 보고 DNAT 규칙을 만드는데, 비어있으니 만들어지지 않은 것.
- **해결책:** `kubectl get endpoints <서비스명>`을 확인하고, 매칭되지 않는 라벨 오타를 찾아 수정해야 합니다.

## 특정 노드에서만 네트워크가 안 돼요

- **증상:** 다른 노드에서는 Service 접속이 잘 되는데, 특정 노드에 뜬 파드들만 유독 통신이 안 됩니다.
- **원리 (NAT 규칙 생성기 결함):** 앞서 말한 DNAT/SNAT 규칙을 노드마다 부지런히 적어주는 '자동화 봇'이 바로 `kube-proxy` . 해당 노드에 떠 있는 `kube-proxy` 파드가 죽어있거나 에러가 나서 규칙 업데이트를 멈춘 상황입니다.
- **해결책:** `kubectl get pods -n kube-system -l k8s-app=kube-proxy -o wide`로 각 노드의 프록시 상태를 확인하고, 죽어있는 애의 로그를 보거나 재시작해야 합니다.

## 파드끼리 통신이 안 돼요 or 외부 인터넷이 안 돼요

- **증상:** 파드에서 외부망으로 `ping 8.8.8.8`이 안 나가거나, 다른 노드에 있는 파드 IP로 직접 핑이 안 갑니다.
- **원리 (라우팅 및 SNAT 관점):** 길 찾기(Routing Decision) 단계에 필요한 가상 네트워크 대역 정보를 제공하거나, 나갈 때 출발지를 위장해주는(SNAT) 역할을 하는 **CNI** (Network Plugin, 예: Flannel, Calico)가 망가진 상황입니다.
- **해결책:** `kube-system` 네임스페이스에서 CNI 파드 상태를 확인하고, CNI 설정 파일(`/etc/cni/net.d/`)이 노드에 제대로 구성되어 있는지 점검해야 합니다.
