# Legacy Linux Network Stack (iptable/netfilter)

## 01. Netfilter 5가지 핵심 Hook
1. PRE_ROUTING
	1. NIC에서 커널로 들어온 직후, 라우팅 결정이 내려지기 전에 실행된다.
2. FORWARD
	1. PRE_ROUTING 이후, 라우팅 결정에서 해당 패킷의 목적지가 로컬 호스트가 아니라고 판단이 되면, 패킷은 forward 처리되고, 이 hook이 트리거된다.
3. INPUT
4. OUTPUT
5. POST_ROUTING

## 02. Netfilter 모듈
- ### raw
	- "추적할 것인가 말 것인가"
	- `conntrack` 보다 먼저 실행되는 유일한 테이블
	- ==특정 패킷을 connection tracking 대상에서 제외==
		- e.g.
			- DNS 서버처럼 초당 수만 개의 단발성 UDP 패킷을 처리하는 경우,
			  모든 패킷을 conntrack에 등록하면, conntrack 테이블이 가득차고 성능이 저하된다. raw에서 불필요 패킷들을 제외하면 이러한 오버헤드를 피할 수 있다.

- ### conntrack
	- "이 패킷이 어떤 연결에 속하는가"
	- Netfilter의 독립 서브 시스템(`nf_conntrack`)이다.
	- 패킷을 보고 다음을 판별한다.
		- 새로운 연결인지 (NEW)
		- 이미 연결돼있는 연결인지 (ESTABLISHED)
		- 기존 연결과 관련된 새 연결인지 (RELATED)
	- 이러한 상태 정보를 기반으로 stateful 방화벽, NAT가 동작한다.
		- `-m state --state ESTABLISHED` 등의 stateful 규칙 동작의 기반.
		- NAT 매핑 정보도 `conntrack` 테이블에 저장된다.

## 03 iptables 테이블의 구분과 역할
- ### mangle
	- 패킷 헤더를 수정한다.
	- 패킷의 속성을 변경하는 테이블.
		- TTL 값, TOS/DSCP 필드 수정(QoS용),  MARK 타겟으로 커널 내부 마크 부여

- ### nat
	- 패킷의 출발지/도착지 IP와 포트를 변환한다.
	- PRE_ROUTING 단계에서는 DNAT (Destination NAT),
	  POS_TROUTING 단계에서는 SNAT(Source NAT)/MASQUERADE 를 수행한다.
		- DNAT (Destination NAT)
			- NAT 테이블에서 수행되며, 패킷의 목적지 IP/포트를 변환한다.
			- 실제 라우팅 이전에 목적지를 변경해야하기 때문에, `NF_INET_PREROUTING` hook 단계에서 처리된다.
			- Kubernetes에서 Service ClusterIP -> Pod IP 변환이 DNAT 규칙(kube-porxy가 생성)으로 동작한다.
	- `nat`는 `conntrack`에 의존한다.
		- NEW 연결의 첫 패킷에만 `nat` 규칙이 평가되고, 이후 같은 연결에 대해서는 `conntrack` 테이블의 매핑을 참조해서 자동 변환한다.
- 
- ### filter
	- 패킷을 통과시킬 지 차단시킬 지 결정한다.
	- `ACCEPT/DROP/REJECT`를 결정하며, 방화벽의 핵심이다.
	- PRE_ROUTING hook에서는 filter 테이블을 확인하지 않고,
	  FORWARD/INPUT/OUTPUT hook에만 존재한다.
		- 라우팅 결정 이전에는 이 패킷이 로컬행인지 forward인지 모르기 때문에, 필터링 결정을 할 수 없기 때문이다.

## 04. Hook 시 사용되는 Netfilter 모듈 및  iptables 테이블
- ### PRE_ROUTING
	- raw
	- conntrack
	- mangle
	- nat
- ### FORWARD
	- mangle
		- 포워딩할 패킷의 헤더를 수정한다.
		- 해당 호스트가 라우터 역할을 할 때, 특정 서브넷에서 오는 트래픽에 QoS 마킹을 변경하거나 TTL을 조정할 수 있다.
	- filter
		- 포워딩할 트래픽에 대한 방화벽 정책을 적용한다.
		- 해당 호스트를 경유하는 트래픽 중 허용할 것과 차단할 것을 결정한다.
			- K8s에서 파드 간 통신 시 호스트의 FORWARD 페인을 통과한다.
	- #참고 raw, nat 테이블이 없는 이유
		- raw에서 수행하는 conntrack 분류는 이미 PRE_ROUTING 단계에서 끝났기 때문이다.
		- nat를 통해 수행되는 DNAT은 PRE_ROUTING 단계에서 이미 수행됐고, SNAT은 다음의 POST_ROUTING 단계에서 수행하면 되기 때문이다.
- ### INPUT
	- mangle
		- 로컬 프로세스에 패킷이 전달되기 직전, 패킷 속성을 변경할 수 있다.
	- filter
		- 로컬 호스트 방화벽의 핵심이다.
		- 외부에서 해당 호스트 서버로 들어오는 트래픽을 허용/차단할 지 결정하는 단계이다.
		- iptables 의 규칙들이 실질적으로 적용되는 단계이다.
			- `iptables -A INPUT -p tcp --dport 22 -j ACCPET`
	- nat
		- 드물게 사용된다. 로컬에 들어오는 패킷의 출발지 주소를 변환하고 싶을 때 사용된다.
- ### OUTPUT
	- raw
		- 로컬에서 생성한 패킷도 conntrack 추적에서 제외할 수 있어야 하기 때문에, 해당 테이블을 참조한다.
	- conntrack
		- 로컬에서 나가는 패킷도 연결 상태를 추적해야 한다.
		- 나가는 패킷으 새 연결의 시작(NEW)인지, 기존 연결에 대한 응답(ESTABLISHED)인지 테이블에 기록해야, 돌아오는 응답 패킷을 ESTABLISHED로 인식하고, INPUT filter 에서 통화시킬 수 있다.
	- mangle
		- 나가는 패킷의 속성을 변경시킬 수 있다.
	- nat (DNAT)
		- 로컬에서 보내는 패킷의 목적지를 변환하는 경우가 있다. 
	- filter
		- 로컬에서 보내는 트래픽도 제어해야 한다.
		- 특정 프로세스가 외부로 나가는 것을 차단하거나, 특정 목적지로의 통신을 금지하는 Outbound 방화벽 정책이 여기서 적용된다.
- ### POST_ROUTING
	- magle
	- nat (SNAT/MASQUERADE)
		- 로컬에서 나가는 패킷의 인터페이스가 확정된 이후, 출발지 주소를 어떤 IP로 변경할 지 결정한다.
		- MASQUERADE는 패킷이 나가는 인터페이스의 IP를 자동으로 출발지로 설정한다.
			- K8s에서 Pod IP가 Node IP로 변환되는 SNAT이 이 hook에서 수행된다.

## Socket
- ### Socket
	- socket은 유저 스페이스와 커널의 네트워크 스택을 연결하는 인터페이스이다.
	- 물리적 실체가 아니라, 커널 내부의 데이터 구조 (`struct socket, struct sock`)이다.
	- 소켓의 핵심 역할
		- "어떤 프로세스가 어떤 주소:포트 조합으로 통신"하는가를 식별하는 것이다.
		- 유저 스페이스에서는 파일 디스크럽터(fd)를 통해 해당 소켓에 접근한다.
		- `read(), write(), send(), recv()` 같은 시스템 콜로 데이터를 주고 받는다.
	- 예시
		- 유저 스페이스 애플리케이션이 '80번 포트에서 TCP' 연결을 받겠다고 한˜다. (`bind + listen)
		- 커널은 80번 포트에 해당하는 소켓 구조체를 만든다.
		- 외부에서 80번 포트로 패킷이 오면, 커널의 TCP 스택이 포트 번호를 보고 해당 소캣을 찾아서 데이터를 전달한다.

- ### Buffer
	- 소켓에는 2개의 버퍼(큐)가 있다.
		- 수신 버퍼
			- 커널이 네트워크에서 받은 데이터를 임시 저장하는 공간이다.
			- TCP 스택이 패킷을 순서에 맞게 재조립하여 완성된 데이터를 수신 버퍼에 넣는다.
			- 애플리케이션이 `recv()`를 호출하면, 수신 버퍼에서 데이터를 가져간다.
			- 애플리케이션이 호출하지 않는다면, 버퍼에 계속 데이터가 찬다. 가득차면 TCP 윈도우가 줄어들어 송신측에 더 이상 데이터를 보내지 않도록 신호를 보낸다.
		- 송신 버퍼
			- 애플리케이션이 `send()`를 호출하면, 데이터가 즉시 네트워크로 나가는 것이 아니라 송신 버퍼에 복사 및 적재된다.
			- TCP 스택이 혼잡 제어, 윈도우 크기 등을 고려해서 적절한 타이밍에 버퍼의 데이터를 패킷으로 만들어 전송한다.
			- 수신측에서 ACK를 보내야, 해당 데이터가 버퍼에서 제거된다.

- ### Socket Buffer
	- `sk_buff` 
		- 리눅스 커널에서 네트워크 패킷 1개를 표현하는 구조체이다.
		- NAPI의 poll 함수가 Ring Buffer에서 패킷 데이터를 꺼내면, 해당 데이터를 감싸는 `sk_buff`  구조체를 할당한다.
		- 단순 데이터 버퍼가 아니라, 구조체인 이유
			- 패킷의 실제 데이터 뿐만 아니라, 패킷이 커널 스택을 올라가면서 필요한 모든 메타데이터들을 함께 담아야 하기 때문이다.
				- 어떤 네트워크 인터페이스로 들어왔는지, L2/L3/L4 각 헤더의 시작 위치는 어디인지, 패킷 길이, 연결 상태, 타임스탬프 등
		- 패킷이 L2 -> L3 -> L4로 올라갈 때, 실제 데이터를 복사하는 게 아니라 `sk_buff` 내부의 포인터만 조정한다.
			- 이러한 설계 덕분에 계층을 올라갈 때마다 패킷의 모든 데이터에 대한 메모리 복사가 발생하지 않는다.

## 05. 구조체 (Struct)
- C에서 구조체란 여러 종류의 정보를 하나로 묶어서 이름을 붙인 것이다. 파이썬의 class와 같으며, 즉 사용자 정의 자료형이다.
- `sk_buff` 구조체는 패킷 데이터 전체를 포함하고 있는 것이 아니라, 패킷에 대한 메타 정보(어떤 NIC로 들어왔는지? 어떤 프로토콜을 사용하는지? 길이가 어느정도인지?) 와 함께 실제 데이터가 있는 위치를 가리키는 포인터를 담고 있다.
	- `Header Pointers`
		- 패킷 데이터 안에서 각 계층의 헤더라 시작되는 위치를 가리킨다.
			- `Ethernet Header` : 이더텟 헤더의 시작점
			- `IP Header` : IP 헤더의  시작점
			- `TCP/UDP Header` : TCP/UDP 헤더의 시작점
		- 패킷이 L2 -> L3 -> L4 로 올라올 때, 커널은 데이터 전체를 복사하는 게 아니라, `sk_buff`  구조체의 이 포인터들만 조정해서, 지금 어느 헤더를 보고 있는가를 바꾼다.

- 구조체란 "관련된 여러 정보를 하나의 이름 아래 묶어둔 묶음"이고, `sk_buff`는 "패킷 하나에 대해 커널이 알아야 할 모든 정보를 묶어둔 묶음"이다.
- 패킷이 커널 네트워크 스택을 이동할 때, 실제로 이동하는 것은 이 `sk_buff` 구조체이며, 패킷 데이터는 메모리에 그대로 있고 구조체의 포인터가 그 위치를 기억하고 있는 것이다.



## 06. NIC -> Device Driver -> CPU 인터럽트 흐름
1. 패킷이 NIC에 도착.
2. NIC H/W가 패킷 데이터를 자신의 내부 Buffer에 임시 저장한다.
3. NIC는 DMA(Direct Memory Access)를 통해, 패킷 데이터를 사전에 미리 할당된 커널 메모리의 Ring Buffer에 직접 복사한다. DMA 방식으로 NIC가 CPU를 거치지 않고 직접 메모리에 데이터를 복사하는 것이 특징이다.
4. DMA 전송이 완료되면, NIC는 하드웨어 인터럽트(IRQ)를 발생 시킨다.


## 07. DMA 시 사용되는 메모리
- NIC가 DMA로 패킷 데이터를 적재하는 메모리 영역은 커널이 부팅 후 드라이버 init 시점에 미리 할당해둔 영역을 사용한다.
- DMA를 위해 할당하는 메모리 영역의 특징
	- 물리적으로 연속된 메모리여야 한다.
		- DMA는 가장 주소가 아니라 물리 주소를 사용해야 하므로, 물리적으로 흩어진 페이지를 사용할 수 없다.
	- NIC 하드웨어어가 접근 가능한 주소 범위에 있어야 한다.
		- 오래된 하드웨어는 읽을 수 있는 메모리 공간 크기의 한계가 있어서, 커널이 이에 호환되는 낮은 주소의 메모리를 할당해야 하는 경우가 있다.
	- CPU 캐시와 일관성이 보장돼야 한다.
		- NIC가 메모리에 쓴 데이터를 CPU가 읽을 때, 캐시에 있는 이전의 값이 아니라, NIC가 쓴 실제 최신 값을 읽어야 한다.
- 세부 과정
	- NIC 드라이버 로드 (`insmod` 또는 부팅 시)
		- 드라이버는 커널에게 "DMA에 쓸 수 있는 메모리를 할당해달라고" 요청한다.
			- `dma_alloc_coherent(), dma_map_single()` 등
	- 드라이버가 커널로부터 DMA 메모리 공간을 할당 받는다.
	- 드라이버는 할당받은 메모리 공간의 물리 주소를 NIC 하드웨어에게 알려준다.
	- NIC는 전달받은 물리 주소를 기억하고, 이후 패킷이 도착하면 NIC는 CPU 개입 없이 해당 주소를 바탕으로 메모리에 직접 패킷 데이터를 쓴다.



## 08. Ring Buffer
- Ring Buffer (또는 Descriptor Ring)은 DMA 메모리 영역을 관리하는 자료구조이다.
- 패킷 데이터 자체를 답는 공간이 아니라, 패킷 데이터가 저장된 위치를 가리키는 디스크립터(Descriptor)의 배열이다.
- Ring Buffer 는 고정 크기의 배열기며, 원형 구조이다.
	- 원형 구조 덕분에 고정된 크기의 메모리를 계속 사용할 수 있고, 동적으로 메모리를 할당/해제할 필요가 없다.
	- 네트워크 패킷은 초당 수백만 개가 올 수 있으므로, 매번 메모리를 할당했다가 해제하면 성능이 저하된다.
	- 따라서, Ring Buffer는 고정 크기의 메모리를 순환하며 재사용함으로써 이러한 문제를 해결한다.
- 배열의 각 엔트리를 "디스크립터"라고 하며, 각 디스크립터에는 2개의 핵심 정보가 들어있다.
	- 1) 패킷 데이터가 저장된 DMA를 위해 할당된 메모리의 물리 주소
	- 2) DMA 를 위해 할당된 메모리의 상태 정보
		- 해당 메모리 공간이 비어있는지, NIC가 데이터를 썼는지 등
