# CNI와 Pod의 통신 흐름

## CNI란

컨테이너 런타임이 네트워크 설정을 외부 플러그인에 위임하기 위한 표준 인터페이스

즉, 

- 컨테이너 네트워크를 어떻게 구성할지를 CNI plugin이 결정
- 컨테이너 런타임(containerd)는 CNI를 호출만 함

+CNI는 컨테이너 네트워크 구성을 담당하며 실제 패킷 전달은 Linux 커널의 네트워크 스택(라우팅, iptables, eBPF 등)에 의해 처리된다.

### 컨테이너 생성 시 CNI plugin의 역할

1. 네트워크 네임스페이스 생성 → container runtime이 수행 후 CNI 호출
2.  veth pair 생성
    
    ```yaml
    # 한 쌍의 인터페이스 생성
    container eth0 <-> host veth
    ```
    
3. host쪽 `veth`를 네트워크에 연결
    - bridge 기반이면 → `cni0` bridge에 attach
    - cilium이면 → eBPF datapath에 attach = 인터페이스에 eBPF hook을 건다
4. IP 할당
    - IPAM plugin이 각 인터페이스 쌍에 ip를 할당
5. container routing 설정
    - 같은 Pod 네트워크 대역은 `eth0`로 직접 통신
    - 외부로 나갈 땐 gateway (=bridge(`cni0` )의 IP)로 전달

→ 이 상태에서는

- 같은 노드 내 Pod 및 host와 통신 가능하며,
- 다른 노드의 Pod 통신은 추가 routing 설정으로 Pod IP 그대로 통신 가능하고,
- 외부 통신을 위해서는 SNAT 설정이 필요하다.

### **A. 동일 노드 내부 Pod 간 통신 (Pod A ↔ Pod B)**

1. Pod A는 목적지 IP(10.244.1.3)가 자신의 서브넷에 있음을 확인하고 해당하는 MAC 주소를 찾기 위해 `eth0`로 ARP 요청을 보냄
2. ARP 요청은 `vethA` 를 통해 호스트의 `cni0` 브리지로 전달된다.
3. `cni0` 는 ARP 요청을 모든 포트에 플러딩한다.
4. Pod B는 자신의 IP에 대한 ARP 요청임을 확인하고 자신의 MAC 주소로 응답한다. 이 응답은 다시 `cni0` 을 거쳐 Pod A로 전달된다.
5. Pod A는 Pod B의 MAC 주소를 학습하고, 데이터를 `cni0` 브리지를 통해 Pod B로 직접 전송한다.

### **B. 노드 간 Pod 통신 (Pod A ↔ Pod C)**

1. Pod A는 목적지 IP(10.244.2.2)가 로컬 서브넷이 아님을 확인하고, 패킷을 기본 게이트웨이인 `cni0` 브리지의 MAC 주소로 전송한다.
2.  `cni0` 는 이 패킷이 자신에게 온 것이지만, 목적지가 다른 IP임을 알고 , 호스트의 네트워킹 스택으로 넘긴다.
3. 호스트 1의 커널은 라우팅 테이블을 확인한다. `10.244.2.0/24` 대역(노드 2의 Pod 대역)으로 가는 패킷의 다음 홉(next hop)이 노드 2의 IP(`192.168.1.11`)로 설정되어 있다. → 이 라우팅 룰은 CNI 플러그인이나 Kube-proxy가 미리 설정해둔다.
4. 커널은 패킷의 원본 IP(Pod A: 10.244.1.2)를 유지한 채, 호스트의 `eth0`을 통해 노드 2로 전송한다.
5. 호스트 2의 커널은 `10.244.2.0/24` 대역이 로컬 `cni0` 브리지로 연결되어 있음을 확인하고, 패킷을 `cni0` 브리지로 넘긴다.
6. `cni0`는 목적지 MAC 주소(Pod C의 eth0 MAC)를 사용하여 패킷을 Pod C에 연결된 `vethC` 포트로 전달한다.
7. Pod C는 원본 IP가 Pod A(10.244.1.2)인 패킷을 수신

### **C. Pod에서 외부 통신 (Pod A → Internet)**

시나리오: Pod A가 `google.com`(예: 8.8.8.8)으로 통신을 시도

1. Pod A는 목적지(8.8.8.8)가 외부임을 확인하고 패킷을 게이트웨이(`cni0`)로 보낸다.
2. 호스트 커널은 패킷을 받아 라우팅 테이블을 확인하고 기본 게이트웨이(외부망으로 나가는 `eth0` )로 패킷을 보내야겠다고 판단
3. 패킷이 호스트의 `eth0`를 통해 외부로 나가기 전에, **iptables의 `POSTROUTING` 체인**에서 **SNAT(Source Network Address Translation)** 처리가 일어난다. 이에 따라 원본 IP(`10.244.1.2`)가 호스트 1의 IP(`192.168.1.10`)로 변경된다.
4. 패킷은 호스트 IP를 원본으로 하여 외부로 나간다. 응답 패킷은 다시 호스트로 돌아오고, iptables가 이를 conntrack 통해서 Pod A로 전달한다.

### **D. 외부에서 Pod 통신 (Internet → Pod A)**

Pod IP는 private IP이므로, 외부에서 직접 접근할 수 없고, Service를 통해 노출해야 한다.

ClusterIP는 내부 통신 용도이므로, 외부 통신을 위해서는 NodePort나 LoadBalancer 유형으로 생성하면 된다.

Service가 생성되면, 보통 **kube-proxy**가 이를 감지하고 iptables NAT table에서 DNAT 규칙을 추가하여 Service IP 또는 NodePort로 들어온 트래픽을 Pod로 전달한다.

시나리오: 외부 클라이언트가 `192.168.1.10:30001` (NodePort)로 접속 시도

```
packet
 ↓
PREROUTING chain
 ↓
KUBE-SERVICES chain
 ↓
KUBE-SVC-XXXXX
 ↓
KUBE-SEP-XXXXX
 ↓
endpoint pod
```

1.  패킷이 노드의 `eth0`에 닿자마자 NAT 테이블의 `PREROUTING` 체인으로 들어간다. 
2. `KUBE-SERVICES`는 모든 서비스 트래픽의 입구로 여기서 패킷의 목적지 포트(30001)를 확인하고 대응하는 서비스 체인인 `KUBE-SVC-XXXX`로 패킷을 넘긴다.
3. `KUBE-SVC-XXXXX`는 만일 해당 서비스에 연결된 Pod이 여러 개라면, 하나의 Pod를 선택한 후, 선택된 Pod의 엔드포인트 체인인 `KUBE-SEP-XXXX` 로 보낸다.
4. `KUBE-SEP-XXXX` 에서 패킷의 목적지를 `192.168.1.10:30001` 에서 실제 `10.244.1.2:80` (Pod A)로 바꾼다.
5. `PROROUTING` 체인에서 패킷의 목적지 IP가 바뀌었으므로, 커널은 패킷을 어디로 보낼지 다시 계산한다. 다시 라우팅 테이블을 확인하고, “목적지가 10.244.1.2네? 이건 `cni0` 브리지에 연결된 애구나!"라고 판단하여 패킷을 브리지 인터페이스로 넘긴다.
6. `FILTER` 테이블의 `FORWARD` 체인을 통과하며 보안 규칙(Network Policy 등)을 체크한다.
7. 패킷이 `cni0` → `vethA` → `eth0(Pod)`  순서로 전달되어 Pod A 내부 앱에 도착

**만약 NodePort로 들어왔는데, 해당 노드에 Pod이 없고 옆 노드에 있다면?"** 

`NodePort` 서비스를 생성하면, 쿠버네티스 클러스터는 모든 노드의 동일한 포트를 연다 

→ 따라서 만약 사용자가 하필 Pod이 없는 노드의 IP로 접속했다면, 해당 노드는 룰에 따라 Pod이 실제 있는 노드로 패킷을 넘겨줘야 한다.

- 감지 시점: `KUBE-SVC` 체인은 자기 노드에 Pod가 있는지 따지지 않고, 전체 엔드포인트(Pod들) 중 하나를 랜덤하게 고른다.
- 선택된 Pod이 옆 노드에 있다면, 그 노드가 패킷을 수락할 수 있도록 목적지 IP를 해당 Pod의 IP로 즉시 변경(DNAT)해야 한다.
    - 원래 목적지: `192.168.1.10:30001` (노드 1)
    - 변경 후 목적지: `10.244.2.2:80` (노드 2에 있는 Pod C)
- 또한, 옆 노드로 보낼 때는 응답이 나(노드)를 거쳐서 돌아올 수 있도록 출발지 IP를 내 IP로 변경(SNAT)해야 한다.
    - 그래서 출발지(Source)를 클라이언트 IP에서 노드 1의 IP(`192.168.1.10`)로 바꾼다.
    
    → 이게 왜 필요한가?
    
    클라이언트의 거절: "난 너랑 말한 적 없어!"
    
    → 나는 노드 1(192.168.1.10)한테 질문을 보냈는데 받은 응답 패킷의 출발지가 왜 노드 2이지? 
    
    → 잘못 배달 패킷? 해킹 시도? → **드랍(Drop)!**
    
    즉, TCP 연결은 `[출발지 IP/포트, 목적지 IP/포트]`라는 4개의 정보가 요청과 응답에서 완벽하게 대칭을 이뤄야 유효하다.
    

Pod에서 패킷이 발생했을 때 로컬/외부 판단)

Pod는 격리된 리눅스 네트워크 네임스페이스이므로, 내부에 자체적인 라우팅 테이블을 갖고 있다. 따라서 패킷이 발생하면,

1. 자신의 IP/서브넷 마스크와 목적지 IP를 비교
    - Pod A의 정보: IP `10.244.1.2`, Mask `255.255.255.0` (/24)
    - 연산 과정: 목적지 IP와 자신의 서브넷 마스크를 AND 연산
        - Case 1 (Pod B: 10.244.1.3): 연산 결과가 `10.244.1.0`입니다. 자신의 네트워크 대역과 일치하므로 로컬 통신으로 판단
        - Case 2 (Google: 8.8.8.8): 연산 결과가 `8.8.0.0`입니다. 자신의 대역과 다르므로 외부 통신으로 판단
2. 라우팅 테이블 조회
