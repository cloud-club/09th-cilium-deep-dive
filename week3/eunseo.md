# 캡슐화

- L2 :  같은 로컬 네트워크
- L3 : 서로 다른 네트워크를 넘어 최종 목적지 IP까지 어떻게 가나
- L4 : 그 목적지 컴퓨터 안의 어떤 프로그램으로 전달하나

상대가 다른 네트워크에 있으면, 최종 목적지의 MAC이 아닌 중간 라우터(게이트웨이)의 MAC으로 보낸다.

Calico에서도, 호스트가 next-hop MAC으로 보이도록 한다. 패킷은 ‘호스트’의 Linux Routing Table과 iptables 또는 eBPF에서 라우팅된다.

# Underlay와 Overlay

- Underlay : 노드들이 실제로 연결되어 있는 진짜 네트워크

  ex. 클라우드 VPC, 데이터센터 fabric, 사내 L3 네트워크

- Overlay: 그 위에 얹는 가상 네트워크

  underlying network가 pod IP를 모르거나 어느 pod가 어느 node에 있는지 모를 때, pod-to-pod 트래픽을 처리하는 네트워크

  Underlay가 처리할 수 없는 내부 패킷을, Underlay가 처리할 수 있는 외부 패킷 안에 넣어서 보냄

    ```python
    원래 내부 패킷:
    Pod A IP → Pod B IP
    
    overlay 캡슐화 후 바깥 패킷:
    Node A IP → Node B IP 안에
    Pod A IP → Pod B IP 를 넣음
    ```


Underlay는 바깥쪽 node IP를 보고 Node B까지 운반한다.

Node B에 도착하면 바깥 껍데기를 벗기고, pod A → pod B 패킷을 꺼내어 로컬 파드에 전달한다.

- Overlay 장점 : underlay 의존성 감소
- Overlay 단점 : 추가 헤더 때문에, CPU와 패킷 크기(MTU)에 비용이 듬

## Overlay vs SNAT

| **구분** | **오버레이 (Overlay) 네트워크** | **SNAT (Source NAT)** |
| --- | --- | --- |
| **통신 목적지** | **클러스터 내부** (다른 노드에 있는 Pod) | **클러스터 외부** (인터넷, 다른 클러스터, 외부 DB 등) |
| **동작 방식** | **캡슐화 (포장)**
Pod IP를 감추고, 겉에 Node IP로 된 새 패킷 헤더를 씌움 | **주소 변환 (바꿔치기)**
출발지 Pod IP를 Node IP로 아예 덮어씀 |
| **왜 하는가?** | 물리 **스위치**(언더레이)들이 Pod IP를 모르니까, 노드 간 배달을 위해 아는 주소(Node IP)로 포장하려고 | 외부 **라우터**들이 Pod IP를 모르니까, 외부에서 답장을 찾아올 수 있는 유효한 공인/사설 주소(Node IP)로 발신자를 바꾸려고 |
| **관여하는 기술** | VXLAN, IPIP (Calico, Flannel 등 CNI가 담당) | iptables, IPVS, eBPF (Kube-proxy 또는 CNI가 담당) |

# VXLAN과 IPIP

Calico는 VXLAN과 IP-in-IP 두가지 캡슐화를 지원한다.

- VXLAN: L3 네트워크에 L2 네트워크를 얹기 위한 overlay 캡슐화 프레임워크
- IP-in-IP: IP 패킷 안에 IP 패킷을 넣는 방식

VXLAN은 BGP가 필수가 아니고, IP-in-IP는 노드 간 BGP를 사용한다.

## Cross-Subnet 모드

Overlay 네트워크 사용 시 : Encapsulation을 하면 되지만, 포장을 씌우고 벗기는 과정에서 비용이 발생한다. 따라서 Cross-Subnet 모드를 사용한다.

### 상황 A: 같은 서브넷 안에서 통신할 때

- 출발지 노드(Node 1)와 목적지 노드(Node 2)가 동일한 L2 스위치에 연결되어 있으며, 중간에 물리 라우터(L3 Gateway)가 존재하지 않음.
1. 경로 탐색 (BGP):
    - 출발지 노드(Node 1)의 OS는 BGP에 의해 사전에 동기화된 라우팅 테이블을 조회.
    - 목적지 파드가 노드 2(Node 2 IP)에 할당된 대역임을 확인.
2. 캡슐화 생략 (Calico가 결정):
    - Calico는 두 노드가 동일한 서브넷에 있음을 인지.
    - 네트워크 오버헤드를 최소화하기 위해 **오버레이(VXLAN/IPIP) 캡슐화를 수행하지 않음.**
3. 물리 주소 학습 (L2 Address Learning):
    - 노드 1은 노드 2로 패킷을 직접 전송하기 위해 ARP 요청을 브로드캐스트
    - **노드 2의 MAC 주소**를 획득
4. 패킷 전달:
    - Pod IP가 그대로 노출된 원본 패킷을 노드2로 직접 전송.

### 상황 B: 서브넷 경계를 넘을 때

- 출발지 노드(Node 1)와 목적지 노드(Node 3)가 서로 다른 L2 대역에 존재하여, 패킷 전송 시 반드시 물리 라우터(L3 Gateway)를 경유해야 함.
1. 경로 탐색 (BGP):
    - 출발지 노드(Node 1)의 OS는 BGP 라우팅 테이블을 조회.
    - 목적지 파드가 노드 3(Node 3 IP)에 있음을 확인하고, 해당 노드로 가기 위해 기본 게이트웨이(Default Gateway)를 거쳐야 함을 인지.
2. 캡슐화 수행 (Calico 결정):
    - Calico는 중간 경로에 위치한 물리 라우터가 내부 사설망인 Pod IP를 인지하지 못해 패킷을 드롭할 것이다를 예상..
    - 원활한 라우터 통과를 위해 원본 패킷 외부에 노드 3의 IP를 목적지로 하는 오버레이 캡슐화(VXLAN 또는 IPIP)를 적용.
3. 물리 주소 학습 (L2 Address Learning):
    - 노드 1은 패킷을 외부 대역으로 보내기 위해, 노드 3이 아닌 속해있는 서브넷의 물리 라우터(Gateway) MAC 주소를 ARP로 획득.
4. 패킷 전달 및 해제:
    - 캡슐화된 패킷이 물리 라우터로 전송됨.
    - 라우터는 캡슐화된 겉포장(Node 3 IP)만 확인하고 일반적인 트래픽으로 간주하여 노드 3의 서브넷으로 정상 라우팅.
    - 노드 3에 도착한 패킷은 Calico에 의해 캡슐화가 해제(Decapsulation)된 후 최종 목적지 파드로 전달됨.

### 효율적인 Cross-Subnet 모드 적용하기

`custom-resources.yaml` 파일 (Calico를 처음 설치할 때 설정파일)

```python
apiVersion: operator.tigera.io/v1
kind: Installation
metadata:
  name: default
spec:
  calicoNetwork:
    ipPools:
    - blockSize: 26
      cidr: 192.168.0.0/16
      encapsulation: VXLANCrossSubnet  <-- 바로 이 부분!!
      natOutgoing: Enabled
      nodeSelector: all()
```

이미 운영중인 클러스터에서는 `kubectl get ippool ~`  명령어를 통해 CrossSubnet 모드인지 확인 가능하다.

# BGP

네트워크의 라우터들 사이에서 라우팅 정보를 교환 표준 프로토콜.

각 node를 가상 라우터처럼 생각하자.

쿠버네티스 클러스터가 구성되면, 각 노드는 자신이 관리할 '파드용 IP 주소 대역(Subnet)'을 할당받는다.

- **Node A:** 내 파드들은 `10.244.1.0/26` 대역을 쓴다.
- **Node B:** 내 파드들은 `10.244.2.0/26` 대역을 쓴다.

Calico를 설치하면 각 노드에 BGP 에이전트(BIRD 등)가 돌아가면서 **가상 라우터 역할**을 한다. 이 에이전트들이 서로 연결(Peer)되어 정보를 교환한다.

- 10.244.1.0/26은 Node A 쪽으로 가면 된다
- 10.244.2.0/26은 Node B 쪽으로 가면 된다

그 결과 각 노드의 운영체제(리눅스) 라우팅 테이블에 기록됨

- Node B의 라우팅 테이블: `10.244.1.0/26 대역으로 가려면 👉 Node A의 IP로 가라`
- Node A의 라우팅 테이블: `10.244.2.0/26 대역으로 가려면 👉 Node B의 IP로 가라`

## Peering

각 BGP router는 하나 이상의 BGP peer를 가지며, 서로 BGP로 통신한다. 그래서 “노드 A가 노드 B와 피어링한다”는 말은 물리 케이블을 꽂는다는 뜻이 아니라, **논리적으로 BGP 세션을 맺고 경로 정보를 교환한다**는 뜻이다.

Calico는 node끼리 피어링할 수도 있고, route reflector와 피어링할 수도 있고, top-of-rack(랙 상단) 물리 라우터와도 피어링할 수 있다. 그래서 Calico는 쿠버네티스 내부만 보는 도구가 아니라, 필요하면 기존 물리 네트워크의 라우팅 체계와도 연결될 수 있는 네트워크 시스템인 것을 알 수 있다.

- **Node-to-Node Peering:** 쿠버네티스 워커 노드 간의 내부 라우팅 정보 교환.
- **Node-to-Reflector Peering:** 노드와 Route Reflector 간의 세션.
- **ToR(Top-of-Rack) Peering:** 클러스터 외부의 물리 네트워크 라우터(데이터센터의 ToR 라우터 등)와의 BGP 세션 연동. 이를 통해 클러스터 내부의 파드(Pod) IP 대역 경로를 기존 레거시 네트워크 인프라에 직접 전파할 수 있습니다.

### full-mesh와 route reflector

- Full-Mesh (풀 메쉬) 토폴로지

  Calico BGP 활성화 시 적용되는 기본(Default) 동작 모드입니다.

    - 구조: 클러스터 내의 모든 노드가 상호 간에 1:1로 직접 BGP 세션을 수립합니다.
    - 특징: 경로 정보가 중간 경유 없이 각 노드로 직접 전달됩니다.
    - 한계점 (Scaling Issue): 노드 수가 N개일 때, 생성되는 BGP 세션의 수는 N(N-1)/2개입니다. 노드 수가 증가할수록 BGP 세션 수와 라우팅 업데이트 트래픽이 기하급수적으로 증가하여 제어 평면(Control Plane)의 과부하를 초래합니다. 일반적으로 100 노드 이하의 중소규모 클러스터에 권장됩니다.
- Route Reflector (라우트 리플렉터) 모델

  규모가 커지면 세션 수가 너무 많아집니다. 그래서 **route reflector**를 둡니다.

    - 구조: 클러스터 내 특정 노드(또는 전용 장비)를 Route Reflector로 지정합니다. 일반 노드들은 서로 직접 피어링하지 않고, Route Reflector와만 단일 BGP 세션을 수립합니다.
    - 동작 원리: 특정 노드에서 라우팅 정보의 변경(파드 생성/삭제 등)이 발생하면, 해당 정보를 Route Reflector로 전송합니다. Route Reflector는 수신한 경로 정보를 자신과 피어링된 다른 모든 노드에게 반사(Reflect)하여 전파합니다.
    - 효과: 노드당 BGP 세션 수를 대폭 감소시켜 네트워크 오버헤드를 최소화하고 안정적인 확장을 가능하게 합니다.

  ⇒ Control Plane 과 Data Plane의 분리
  : Route Reflector는 BGP 경로 정보를 분배하는 중앙 집중형 허브 역할만 수행하며, 실제 트래픽의 병목 구간(Bottleneck)이 되지 않는다.


# Calico

각 노드는 자기 파드들을 뒤에 둔 작은 라우터이자 방화벽이다.

- CNI Plugin (컨테이너 네트워크 인터페이스 플러그인)
    - 역할: 파드(컨테이너)의 네트워크 인터페이스를 생성하고, 이를 호스트(노드)의 네트워크 네임스페이스와 연결하는 논리적 링크(`veth` 페어 등)를 구성합니다.
- IPAM Plugin (IP 주소 관리 플러그인)
    - 역할: 사전에 정의된 IP Pool에서 새로 생성되는 파드에 고유한 IP 주소를 동적으로 할당하고 관리합니다.
- Felix (Calico 에이전트 데몬)
    - 역할: 각 노드에서 실행되는 핵심 제어 프로세스입니다. 중앙의 데이터스토어(etcd 또는 Kubernetes API)에서 구성 및 정책을 읽어와 리눅스 커널에 직접 프로그래밍합니다.
    - 세부 기능:
        - 호스트가 워크로드(파드)의 ARP 요청에 응답하도록 설정.
        - IP 포워딩(IP Forwarding) 활성화.
        - 리눅스 커널의 FIB(Forwarding Information Base, 라우팅 테이블)에 파드 엔드포인트 경로(Route) 삽입.
        - `iptables` 또는 `eBPF`를 조작하여 NetworkPolicy에 기반한 ACL(접근 제어 목록) 방화벽 규칙 적용.
- BIRD (BGP 라우팅 데몬)
    - 역할: 표준 BGP(Border Gateway Protocol) 프로토콜 클라이언트입니다. Felix가 리눅스 커널에 프로그래밍한 라우팅 정보(파드 IP 경로)를 수집하여, 클러스터 내 다른 노드의 BGP Peer 또는 외부 물리 라우터로 배포(Advertisement)합니다.

### 경우 1: 같은 노드에 있는 파드끼리 통신

출발지 파드 A와 목적지 파드 B가 동일한 호스트(노드) 내에 위치하는 경우입니다.

- **라우팅 흐름:**
    1. 파드 A에서 발생한 패킷이 호스트의 네트워크 네임스페이스로 전달됨.
    2. 호스트의 리눅스 커널 라우팅 테이블이 목적지 파드 B가 로컬에 있음을 확인.
    3. 패킷이 노드 외부로 나가지 않고 파드 B의 인터페이스로 즉시 전달됨.
- **특징:**
    - 네트워크 패킷이 물리적 NIC(네트워크 인터페이스 카드)를 거치지 않으므로 BGP 라우팅 및 오버레이(Overlay) 캡슐화가 적용되지 않습니다.
    - 라우팅은 단순화되지만, Felix가 커널에 주입한 `iptables`/`eBPF` 방화벽 정책은 엄격하게 적용되어 트래픽 필터링을 수행합니다.

### 경우 2: 다른 노드이고, underlay가 pod IP를 알 수 있는 경우

출발지 파드 A(Node A)와 목적지 파드 B(Node B)가 서로 다른 노드에 위치하며, 하위 물리 네트워크 장비가 파드 대역(Pod IP CIDR)의 라우팅 경로를 알고 있는 경우입니다.

- **라우팅 흐름:**
    1. Node A의 커널 라우팅 테이블(BIRD에 의해 학습됨)이 파드 B의 대역이 Node B 방향임을 확인.
    2. Node A는 별도의 캡슐화(Encapsulation) 없이 원본 IP 패킷(Native IP Packet)을 Node B로 전송.
    3. 물리 라우터/스위치 역시는 BGP 등을 통해 파드 경로를 인지하고 있으므로 정상적으로 Node B로 패킷 전달.
- **특징:**
    - 오버레이 캡슐화/디캡슐화 과정이 생략되어 가장 높은 네트워크 처리량(Throughput)과 최저 지연 시간(Low Latency)을 보장하는 Calico의 최적화된 통신 방식입니다.

### 경우 3: 다른 노드이고, underlay가 pod IP를 모르는 경우

출발지 파드 A와 목적지 파드 B가 서로 다른 노드에 위치하나, 하위 물리 네트워크(퍼블릭 클라우드, 엄격한 사내 라우터 등)가 클러스터 내부 사설망인 파드 IP를 인식하지 못해 패킷을 드롭(Drop)하는 환경입니다.

- **라우팅 흐름:**
    1. Node A는 외부 네트워크 라우터를 통과하기 위해, 파드 A에서 파드 B로 향하는 원본 패킷의 외부에 Node A에서 Node B로 향하는 패킷(Node IP 목적지)으로 캡슐화(VXLAN 또는 IP-in-IP)를 수행.
    2. 물리 네트워크 장비는 외부 캡슐화에 명시된 Node IP만을 참조하여 Node B로 패킷 전달.
    3. Node B는 수신한 패킷의 외부 캡슐화를 해제(Decapsulation)하고, 내부에 포함된 원본 목적지(파드 B IP)를 확인하여 로컬 파드 B로 전달.
- **특징:**
    - 캡슐화 과정에서 약간의 연산 오버헤드와 패킷 크기 증가가 발생합니다.
    - 물리 네트워크의 제약 구조와 무관하게 클러스터 전역의 파드 통신을 보장하는 범용적인 연결 방식을 제공합니다.

---

- 파드가 생기면 Calico CNI와 IPAM이 IP를 붙인다.
- Felix가 그 노드 커널에 인터페이스, 경로, ACL을 넣는다.
- 같은 노드 통신이면 로컬 라우팅으로 끝난다.
- 다른 노드 통신이면, underlay가 pod IP를 알 수 있으면 BGP/정적 라우트 등을 바탕으로 **직접 라우팅**한다.
- underlay가 pod IP를 모르면 VXLAN 또는 IP-in-IP로 **캡슐화**해서 보낸다.
- 어느 경우든 정책은 각 노드의 iptables/eBPF에서 **허용/차단**된다.
